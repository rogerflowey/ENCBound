# sk-sgx: bounded integration and sealed-handle read control

Date: 2026-10-21. Source: `mfriedl/sk-sgx` at
`7368dfb3b95092e13c54191c93a79be668db24ef` (pins in
[`apps/sk-sgx/pins.json`](../apps/sk-sgx/pins.json)). Backend: Intel SGX SDK
2.26 simulation, one sequential TCS. The machine-readable record is
[`2026-10-21-sk-sgx.json`](2026-10-21-sk-sgx.json); reproduction is in
[`apps/sk-sgx/README.md`](../apps/sk-sgx/README.md).

This record separates three things: (1) the bounded ten-unit enclave closure
runs in four SDK SIM configurations; (2) the native adapter contracts pass;
(3) a real sealed-handle out-of-bounds read in the pinned enclave is attributed
in native ASan and BASELINE, and the protected profiles reject the dangerous
short-handle request at the checked sealing adapter. It is not a hardware,
performance or general exploit-prevention result.

## 1. Bounded application closure

The complete non-debug trusted closure contains ten pinned application units:
`enclave`, `ed25519`, `fe25519`, `ge25519`, `sc25519`, `sha256blocks`,
`sha256hash`, `sha512blocks`, `sha512hash` and `verify`. The original `sk.edl`
has three ECALLs and the debug `ocall_puts` declaration. The untrusted provider
`sk-sgx.c` remains the original SK v4 provider; the host oracle uses the
original ECALLs and verifies every successful Ed25519 signature independently
with OpenSSL.

The closure is admitted with the all-compat preset and the scalar frontend
(`-O2 -fno-vectorize -fno-slp-vectorize`). The default vectorized frontend is
rejected for `fe25519` and `verify` because the pass does not admit
`llvm.vector.reduce.*`; this is a real admission limitation, not a runtime
choice. One explicit source adaptation is recorded:
`malloc(aadlen)` → `malloc(aadlen ? aadlen : 1)` preserves the pinned empty-AAD
path under the checked allocator. It is identical in all profiles.

Fresh results:

| Configuration | Mode | Calls | Verified signatures | Closure audit |
| --- | --- | ---: | ---: | --- |
| BASELINE | SDK SIM | 68 | 21 | complete |
| RADIX_ONLY | SDK SIM | 68 | 21 | complete |
| MAC27 | SDK SIM | 68 | 21 | complete |

Totals: **4 configurations / 272 direct ECALLs / 12 provider ECALLs / 84
OpenSSL-verified signatures**. Native adapter contracts report
`sk_sgx_adapters_test 54 checks, 0 failures` and `56 checks, 0 failures` (the
MAC27 row adds the tag-forgery control). Three protected configurations have a

`crypto_sign_ed25519_ref_fe25519_add`; it is an observation of the inserted
check and raw conversion, not an attack result. The recorded replay checks 870
retained hashes and repeats all four complete ownership/closure audits.

The host exercises the original error paths (null application/output, short or
missing buffers, wrong application, damaged key handle, wrong signature
length), repeated signatures, the provider path and a 4096-byte application
name. The 64 MiB allocation demand for the six-byte application is rejected by
the enclave resource limit without breaking the session.

## 2. Finding: undersized sealed key handle

`ecall_sk_sign_ed25519` casts the `[in, size=key_handle_len]` handle to
`sgx_sealed_data_t` and calls SDK accessors before checking `key_handle_len`
against a required sealed size:

```c
const sgx_sealed_data_t *sealed = (const sgx_sealed_data_t *)key_handle;
...
sklen = sgx_get_encrypt_txt_len(sealed);          /* enclave.c:178 */
if (sklen != sizeof(sk)) ...
...
aadlen = sgx_get_add_mac_txt_len(sealed);         /* enclave.c:189 */
```

The EDL bridge copies exactly `key_handle_len` bytes into a trusted buffer.
For the pinned SDK 2.26 the compiled layout is:

| Field | Offset |
| --- | ---: |
| `sizeof(sgx_sealed_data_t)` | 560 |
| `plain_text_offset` | 512 |
| `aes_data.payload_size` | 528 |

The SDK header comments say 64 and 80, and the earlier screening hypothesis
used those values; the compiler and `offsetof` show 512 and 528. The control
asserts the real layout and fails if the pinned header changes.

A 1-byte handle therefore reads bytes 512..515 in `sgx_get_encrypt_txt_len`
before any size check. A 516-byte handle whose in-bounds `plain_text_offset` is
64 passes the first accessor and reads bytes 528..531 in
`sgx_get_add_mac_txt_len`. Both are CWE-125 heap-buffer-overflow reads of the
EDL-declared trusted copy. The untrusted host controls both the length and the
bytes, so the ECALL boundary is reachable directly; the original provider also
passes a caller-supplied handle length through to this ECALL. The read values
influence control flow and are not returned to the host; the sealing MAC still
prevents using a forged header. No exploit or information leak is claimed.

## 3. Native ASan differential

`vuln_native.c` links the unmodified `enclave.c` and the pinned SDK's real
`tSeal_util.cpp` under AddressSanitizer. Non-reached random/seal/unseal
services are aborting stubs, so a control cannot take an unmodeled path.

| Request | Result |
| --- | --- |
| `h0`: 560-byte full header | `-1`, no ASan report |
| `h1`: 1-byte handle | `heap-buffer-overflow`, `READ of size 4`, `sgx_get_encrypt_txt_len`, caller `enclave.c:178`; 511 bytes after the 1-byte region |
| `h2`: 516-byte handle, `plain_text_offset=64` | `heap-buffer-overflow`, `READ of size 4`, `sgx_get_add_mac_txt_len`, caller `enclave.c:189`; 12 bytes after the 516-byte region |

The exact reports are in
`build/sk-sgx/current-2026-10-21/vuln/native/h1.log` and `h2.log`. This is
native, non-SGX evidence; it proves the source-level access with the real
accessor implementation.

## 4. SDK SIM differential

`vuln_host.c` runs the same two requests against each signed SIM enclave. The
host's own allocation is the EDL backing buffer; the enclave performs the
trusted copy.

| Configuration | `h1` (1 byte) | `h2` (516 bytes) |
| --- | --- | --- |
| BASELINE | read watchpoint at byte 512 fires in `sgx_get_encrypt_txt_len`, caller `enclave.c:178`; returns `-1` | read watchpoint at byte 528 fires in `sgx_get_add_mac_txt_len`, caller `enclave.c:189`; returns `-1` |
| RADIX_ONLY | terminal `SIGILL`, `encbound_abort(code=4)` in `encbound_sk_get_encrypt_txt_len` (`adapters.c:51`), caller `enclave.c:178`, through `sgx_ecall_sk_sign_ed25519` | no abort; the 1024-byte rounded slot contains both reads; the original length check returns `-1` |
| MAC27 | same attributed RANGE rejection | same `-1` completion, no abort |
| MAC27-high | same attributed RANGE rejection at base `0x140000000` | same `-1` completion, no abort |

Representative protected attribution (RADIX_ONLY; the capability radix is 4,
a 16-byte slot for the 1-byte request):

```text
Program received signal SIGILL, Illegal instruction.
encbound_abort (code=4) at sdk/platform_layout.c:459
#0  encbound_abort (code=4)
#1  encbound_sk_get_encrypt_txt_len (sealed=0x2000000001000030) at apps/sk-sgx/adapters.c:51
#2  ecall_sk_sign_ed25519 (... key_handle_len=1 ...) at .../prepared/enclave.c:178
#3  sgx_ecall_sk_sign_ed25519 (...) at .../generated/sk_t.c:423
```

The `h2` RADIX_ONLY slot is 1024 bytes (`capability=0x5000000001000400`); the
first accessor returns 64 and the host receives `-1` from the original
application checks. MAC27 and MAC27-high have the same allocation geometry by
design; their capability carries a tag, so the control records the capability
but does not decode a slot radix from it.

The protected enforcement here is the **trusted checked adapter**, not a
compiler-inserted check at the original access. The adapter receives a
capability and checks the complete 560-byte header before calling the raw SDK
accessor. The original application access at `enclave.c:178/189` is not
re-instrumented as a direct struct load.

### Other hypotheses and non-spatial observations

The earlier screening also noted the `SK_DEBUG` AAD-mismatch `%s` read. The
pinned `sk.edl` defines `SK_DEBUG` for edge generation, but `enclave.c`'s
formatter is compiled only when the C compiler defines `SK_DEBUG`; this closure
is non-debug and does not include it. If someone builds with `-DSK_DEBUG`, that
path is a second CWE-125/CWE-170 read: `unsealed_application` is
`malloc(aadlen)` without a NUL terminator and is passed to `%s`.

The following are security-relevant but **not spatial-memory findings**, and
ENCBound's checks do not address them:

- The EDL marks the signature `counter` as `[out]`; the bridge zeroes the cell,
  `ecall_sk_sign_ed25519` reads it before writing, and every signature carries
  counter 0. This defeats the FIDO signature-counter clone/rollback signal.
- `sk_enroll` ignores `challenge`, `challenge_len` and `flags`, returns an empty
  signature and no attestation certificate. `sk_sign` ignores `pin`; `flags` is
  only included in the signed blob, not enforced as user-presence or
  user-verification policy. The provider is therefore a key-sealing demo, not a
  complete FIDO authenticator.
- `enclave.config.tmpl.xml` keeps `DisableDebug=0` and the host always passes
  `SGX_DEBUG_FLAG`; this matches the upstream demo, but a hardware deployment
  would be debuggable. The "non-debug" label in this record refers to the
  `SK_DEBUG` formatter, not the SGX debug attribute.
- The provider creates and destroys an enclave per call using a global
  `global_eid`; concurrent calls are not synchronized. This is a host-side
  thread-safety issue (if mapped, CWE-362), not an enclave memory-safety result.
  `sk_load_resident_keys` returns `SSH_SK_ERR_UNSUPPORTED`.

## 5. What this establishes and what it does not

Established:

- The pinned ten-unit closure admits and runs in BASELINE, RADIX_ONLY, MAC27
  and high-base MAC27 with complete ownership/closure audits and independent
  signature verification.
- The undersized-handle read is a real native heap-buffer-overflow read in the
  pinned source and real SDK accessor implementation.
- BASELINE performs the read in SDK SIM; RADIX_ONLY, MAC27 and MAC27-high
  terminate the 1-byte request with an attributed RANGE abort inside the
  checked sealing adapter before the raw accessor.

Not established / limits:

- Only the 1-byte request is spatially rejected in protected profiles. A
  516-byte request is rounded to a 1024-byte slot; both accessor reads stay
  inside that allocation and read uninitialized padding. ENCBound does not
  claim uninitialized-memory safety or a logical-EDL-length check here.
- The `SK_DEBUG` AAD-mismatch `%s` read (a non-NUL-terminated
  `malloc(aadlen)` buffer) is outside this non-debug closure.
- The host oracle and the vulnerability control are not a full OpenSSH
  client/server workflow. The original provider's resident-key path returns
  `SSH_SK_ERR_UNSUPPORTED`.
- The default vectorized frontend is rejected; the scalar frontend is a
  required configuration, and the `malloc(0)` adaptation is an explicit source
  change.
- No hardware execution, timing, performance, exploit, confidentiality,
  temporal-safety, MAC-advantage or general vulnerability-prevention claim.
  Valid tagged accesses and native adapter rejections are separate rows.
- The frozen experiment targets, pointer mechanism, protected scope, trusted
  boundary and backend are unchanged.

## 6. Reproduction

```sh
# Benign configuration (repeat for BASELINE, MAC27, and MAC27-high):
python3 apps/sk-sgx/probe.py --profile RADIX_ONLY --scalar \
  --out build/sk-sgx/current-2026-10-21/RADIX_ONLY
python3 apps/sk-sgx/finish.py \
  --build build/sk-sgx/current-2026-10-21/RADIX_ONLY --base 0x40000000
python3 apps/sk-sgx/trace.py \
  --build build/sk-sgx/current-2026-10-21/RADIX_ONLY

# Native adapter contracts and vectorized admission rejection:
python3 apps/sk-sgx/native.py --out build/sk-sgx/current-2026-10-21/native
python3 apps/sk-sgx/probe.py --profile MAC27 \
  --out build/sk-sgx/current-2026-10-21/vector-admission

# Sealed-handle native ASan + SDK SIM control:
python3 apps/sk-sgx/vuln.py \
  --build-root build/sk-sgx/current-2026-10-21 \
  --output build/sk-sgx/current-2026-10-21/vuln.json

# Collect and replay:
python3 apps/sk-sgx/record.py \
  --build-root build/sk-sgx/current-2026-10-21 \
  --output evidence/2026-10-21-sk-sgx.json
python3 apps/sk-sgx/record.py --verify evidence/2026-10-21-sk-sgx.json
python3 apps/sk-sgx/vuln.py --verify build/sk-sgx/current-2026-10-21/vuln.json
```

The build root keeps the signed images, original/checked IR, integration
manifests, ownership records, GDB scripts, host binaries and logs. The replay
checks content hashes and repeats the four closure audits; it does not rebuild.
