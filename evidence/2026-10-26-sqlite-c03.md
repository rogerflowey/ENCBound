# SGX_SQLite C03 hostile ingress — 2026-10-26

This record advances the pinned `yerzhan7/SGX_SQLite` selected serial Unix-VFS
route with the C03 control from
[V2–V4-INTEGRATION](../research/nontrivial-ingress-bugs/V2-V4-INTEGRATION.md#c03--sgx_sqlite-ocall-getenv-return-cached-in-azdirs).
The upstream checkout is unchanged. The result is SDK simulation only.

## What was built

`apps/sqlite-sgx/run.py` is now a reproducible recipe for the selected closure.
It regenerates the bridge, private instrumented libc++ archive, application and
trusted objects, then links, signs, audits and runs:

- BASELINE at `0x40000000`;
- RADIX_ONLY at `0x40000000`;
- MAC27 at `0x40000000`;
- MAC27 at `0x140000000`.

Artifacts are retained under `build/sqlite-sgx-c03/`; the machine-readable
record is [results.json](../build/sqlite-sgx-c03/results.json) and the
[curated evidence](2026-10-26-sqlite-c03.json). The recipe compiled and placed
the application and private-library closure in every profile, passed the
application errno, variadic-callback, global-ownership, SDK binary/EDL pin,
exact archive-inventory and metadata audits, and signed each image. `Enclave_t.h`, `Enclave_u.c` and `Enclave_u.h`
match stock in BASELINE; `Enclave_t.c` differs only by the selected
`propagate_errno` extension. No stock-bridge equality is claimed for that file.

## Temp-file trigger

The small DEMO-MATRIX query does **not** reach `unixTempFileDir` in this route.
The selected trigger is a deterministic temp-database spill:

```sql
PRAGMA temp_store=FILE;
PRAGMA temp.cache_size=10;
CREATE TEMP TABLE t(x);
WITH RECURSIVE c(x) AS (SELECT 1 UNION ALL SELECT x+1 FROM c WHERE x<10000)
  INSERT INTO t SELECT x FROM c;
SELECT x FROM t ORDER BY x DESC LIMIT 3;
```

Both BASELINE and the protected profiles print `x = 10000, 9999, 9998`, call
`getenv("SQLITE_TMPDIR")`, `getenv("TMPDIR")`, `stat`/`access` on the selected
directory and open `/var/tmp/etilqs_*` (or the selected directory). The benign
control leaves `TMPDIR` and `SQLITE_TMPDIR` unset and uses `/var/tmp`; it opens
one temp file in each of two ECALL phases and never sees the canary.

## C03 control

The local adaptation adds one writable application global:

```c
char encbound_c03_canary[64] = "C03-PROTECTED-CANARY-8f4d2a";
```

In protected profiles the placement pass puts it in `.encbound.globalrw` with a
global-capability cell; in BASELINE it is ordinary writable application data in
`.encbound.apprw`. The untrusted host, in hostile mode, returns its address from
`ocall_getenv("SQLITE_TMPDIR")` and returns the host environment value for
`TMPDIR` (unset here). The enclave caches the raw value in
`unixTempFileDir.azDirs[0]`, then uses it as the `[in,string]` path of
`ocall_stat`. The host logs only the bytes the bridge actually copies.

The sequence is two ECALL phases with a close/reopen between them. This tests
the V4 static alias as well as the V2 return:

| Row | Canary target | Benign | Hostile |
| --- | --- | --- | --- |
| BASELINE `0x40000000` | `0x400ed6b0`, `.encbound.apprw` (writable, COMPAT) | pass; two temp files; no canary | pass; phase 1 `hostile_getenv=1`, `canary_stat=1`, `temp_open=1`; phase 2 `hostile_getenv=0`, `canary_stat=1`, `temp_open=1` |
| RADIX_ONLY `0x40000000` | `0x40306400`, `.encbound.globalrw` (PROTECTED) | pass; two temp files; no canary | SIGILL, `ENCBOUND_ERR_POLICY` (3) |
| MAC27 `0x40000000` | `0x40306400`, `.encbound.globalrw` (PROTECTED) | pass; two temp files; no canary | SIGILL, `ENCBOUND_ERR_POLICY` (3) |
| MAC27 `0x140000000` | `0x140306400`, `.encbound.globalrw` (PROTECTED) | pass; two temp files; no canary | SIGILL, `ENCBOUND_ERR_POLICY` (3) |

BASELINE host log, both phases (abridged):

```text
[c03] hostile getenv(SQLITE_TMPDIR) -> 0x400ed6b0
[c03] getenv(TMPDIR) -> (nil)
[c03] ocall_stat received canary path: "C03-PROTECTED-CANARY-8f4d2a"
[c03] temp file open: "/var/tmp/etilqs_49f300eec9535899"
[c03] getenv(TMPDIR) -> (nil)
[c03] ocall_stat received canary path: "C03-PROTECTED-CANARY-8f4d2a"
[c03] temp file open: "/var/tmp/etilqs_ecb10fbb7afdd9a5"
```

The single `SQLITE_TMPDIR` getenv across two ECALLs, with a canary stat in both,
is the observed V4 cache reuse. The canary is copied to the host through the
`ocall_stat` `[in,string]` bridge; the evidence does not read enclave memory
from the host.

Protected profiles stop before the host callback. GDB attributes the stop to
the checked bridge string scan, not to a later SQLite access:

## What this establishes

- The selected route reaches `unixTempFileDir` and the subsequent temp-file
  services with the real pinned SQLite code.
- An OCALL-returned raw enclave address is cached in static `azDirs` and reused
  across an ECALL boundary (BASELINE observation).
- BASELINE copies the protected canary to the untrusted host twice, through the
  ordinary `[in,string]` `ocall_stat` bridge.
- RADIX_ONLY at `0x40000000`, and MAC27 at both image bases, reject the
  protected target before the host callback with `ENCBOUND_ERR_POLICY` (3) at
  `encbound_bridge_string` in `ocall_stat`.

## Limits and qualifications

- **This is boundary-service enforcement**, not a later SQLite object check.
  The stop is the checked OCALL string copy.
- **Only PROTECTED targets are rejected.** The design classifies application
  read-only data as COMPAT and admits raw pointers to it. An earlier ad hoc
  MAC27 probe returned the address of the enclave's read-only `/var/tmp` string;
  the bridge accepted it and the host received `/var/tmp`. The C03 control
  therefore uses a writable protected canary. A read-only target would not
  demonstrate protection.
- A normal host `TMPDIR`/`SQLITE_TMPDIR` value is a raw host pointer. The
  protected bridge also rejects that value; the benign control leaves both
  variables unset and uses `/var/tmp`. This is the upstream
  `getenv`-returns-host-pointer limitation, not a C03-specific protection
  result. Fixing it would require an application service that copies host data
  into enclave-owned storage; it is outside this record.
- In protected profiles the first hostile use aborts, so the later `azDirs`
  reuse is not observable past that abort. V4 is demonstrated in BASELINE; the
  protected result is the first-use rejection.
- The host knows the enclave base and the canary offset. No ASLR or
  address-secrecy claim is made.
- SDK simulation only. No SGX hardware isolation, timing, performance, WAL,
  mmap, concurrency, full POSIX or full SQLite compatibility is claimed. The
  selected route remains serial rollback-journal SQLite with mmap and WAL
  disabled.

## Reproduction

```sh
tools/with-integration-defaults.sh python3 apps/sqlite-sgx/run.py \
  --build build/sqlite-sgx-c03 \
  --profile BASELINE --profile RADIX_ONLY --profile MAC27
```

The recipe rebuilds the pass and bridge generator, verifies the pinned source
hashes, builds the private libc++ archive and closure per profile, runs the
normal and hostile rows, attributes protected stops in GDB, and writes
`results.json` and `commands.json`. The script does not modify the pinned
upstream checkout. The only application adaptation for this control is the
canary global and the host harness in `apps/sqlite-sgx/c03_*.c`.

A second clean build into a different directory reproduced the admitted
inventory, all three private libc++ archive hashes, the canary addresses and
sections, the benign/hostile phase counts, and the protected abort code and
attribution. The per-profile `.text` sections were byte-identical. The retained
second-build row record is
[the repro results](repros/2026-10-26-sqlite-c03-repro-results.json). Full
unsigned ELF hashes differ across build directories (generated-path/debug and
link metadata); signed hashes also differ because each build uses a fresh key.
No byte-identical-ELF claim is made.
